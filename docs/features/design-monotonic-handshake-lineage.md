# Design Doc: Monotonic Handshake Lineage (MHL)
**Status:** Draft
**Created:** 2026-07-14

## 1. Context and Scope
"Mailbox Echo Poisoning"—where subagents replay stale but cryptographically valid coordination messages to trick teammates—has emerged as a major vulnerability in horizontal swarms (e.g., Claude Code Agent Teams). Current session-bound tokens prevent cross-session attacks but do not address "intra-session replays" within complex, multi-hop mesh coordination.

MCP Any must implement Monotonic Handshake Lineage (MHL) to ensure that every coordination fragment is unique, non-reusable, and cryptographically linked to a strictly increasing counter anchored to the mission root.

## 2. Goals & Non-Goals
* **Goals:**
    * Assign a unique, monotonic lineage token to every inter-agent coordination message (Mailbox fragment).
    * Enforce a "No-Replay" policy at the T2T Bridge by rejecting any message with a stale or duplicated counter.
    * Provide hardware-attested provenance for the entire sequence of instructions within a mission.
* **Non-Goals:**
    * MHL will not replace the underlying transport encryption (mTLS/LOWA) but will add a semantic integrity layer on top of it.
    * It will not manage the content of the reasoning traces, only the integrity of their delivery sequence.

## 3. Critical User Journey (CUJ)
* **User Persona:** Local LLM Swarm Orchestrator
* **Primary Goal:** Prevent a specialist subagent from re-triggering a high-stakes tool call (e.g., `git push`) by replaying a previous authorized handshake message.
* **The Happy Path (Tasks):**
    1. Parent Agent issues an instruction to Specialist A with MHL Counter `N`.
    2. Specialist A executes and responds to Parent with MHL Counter `N+1`.
    3. If Specialist A attempts to replay the Parent's instruction by sending message `N` to Specialist B, the T2T Bridge detects the stale counter.
    4. The Bridge interdicts the message and quarantines Specialist A for "Lineage Violation."

## 4. Design & Architecture
* **System Flow:**
    * [Parent Request] -> [MHL Minting Service] -> [Signed Message Fragment] -> [T2T Bridge Validator] -> [Target Mailbox].
* **APIs / Interfaces:**
    * `POST /v1/mhl/mint`: Mint a new monotonic token for a sub-mission branch.
    * `POST /v1/mhl/validate`: Validate the lineage of an incoming coordination fragment.
* **Data Storage/State:**
    * A lightweight `MonotonicRegistry` (SQLite) stores the current high-water mark for every mission-root and its branches.

## 5. Alternatives Considered
* **Time-to-Live (TTL) Mailboxes:** Expiring messages after 30 seconds. Rejected because complex reasoning steps often exceed short TTLs, leading to false positives and coordination stalls.
* **Bloom Filters for Replay Detection:** Tracking message hashes. Rejected because it only detects identical replays, whereas MHL provides a structural "Sequence Proof" that is more resilient.

## 6. Cross-Cutting Concerns
* **Security (Zero Trust):** The MHL counter is cryptographically bound to the TPM-signed Mission-Root identity. Tokens cannot be generated by subagents themselves.
* **Observability:** "Sequence Breaks" or "Stale Counter" events are flagged in the `MeshSecurityMonitor` as potential Coordination Hijacking attempts.

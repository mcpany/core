# Design Doc: Active Reasoning Erasure (ARE) Controller
**Status:** Draft
**Created:** 2026-06-18

## 1. Context and Scope
As agent swarms scale and subagents become more autonomous, the volume of intermediate reasoning monologues stored on the Shared Blackboard has increased significantly. This persistent "Cognitive Trail" has become a high-value target for "Reasoning Recovery" exploits, where attackers harvest discarded traces to reconstruct sensitive mission constraints.

The Active Reasoning Erasure (ARE) Controller introduces a mandatory "Cognitive Reaper" service. It ensures that all intermediate reasoning fragments generated by specialized subagents are cryptographically scrubbed from the Blackboard immediately upon sub-task completion or branch termination, leaving only the verified "Mission Mainline."

## 2. Goals & Non-Goals
* **Goals:**
    * Implement an authoritative controller for the cryptographic erasure of subagent reasoning monologues.
    * Mandate "Erasure-at-Termination" for all mission-bound sub-tasks.
    * Provide hardware-attested "Erasure Receipts" to the mission root.
    * Integrate with the Blackboard's versioning hub to ensure no "Ghost Fragments" remain in historical snapshots.
* **Non-Goals:**
    * Deleting the primary mission-root intent (must be preserved for audit).
    * Scrubbing tool outputs (handled by the Differential Context Guard).
    * Managing real-time reasoning (handled by the ARI Hub).

## 3. Critical User Journey (CUJ)
* **User Persona:** Swarm Security Architect
* **Primary Goal:** Ensure that a specialized subagent's internal reasoning (which may contain proprietary logic or temporary credentials) is completely erased once its task is finished.
* **The Happy Path (Tasks):**
    1. Parent Agent spawns a specialist subagent for a sensitive data analysis task.
    2. The ARE Controller assigns a unique "Erasure Scope" to the subagent's session.
    3. The subagent writes its internal monologue fragments to the Blackboard within its assigned scope.
    4. Upon task completion, the subagent signals `TERM` to the ARE Controller.
    5. The ARE Controller executes a cryptographic wipe of the assigned scope on the Blackboard.
    6. The ARE Controller issues a hardware-attested "Erasure Receipt" to the Parent Agent.
    7. The Parent Agent proceeds, knowing that no sensitive intermediate traces remain.

## 4. Design & Architecture
* **System Flow:**
    ```mermaid
    graph TD
        A[Subagent Session Start] --> B[ARE Controller]
        B --> C[Assign Erasure Scope]
        D[Subagent Monologue] --> E[Blackboard: Scoped Region]
        F[Subagent Task Completion] --> B
        B --> G[Cryptographic Wipe of Scoped Region]
        G --> H[Blackboard: Commit Erasure]
        H --> I[Issue Erasure Receipt]
        I --> J[Parent Agent]
    ```
* **APIs / Interfaces:**
    * `are.InitScope(sessionToken) -> scopeID`: Initializes an erasure-tracked scope.
    * `are.TriggerErasure(scopeID) -> Receipt`: Executes scrubbing and returns attestation.
* **Data Storage/State:**
    * **Scope Registry:** An ephemeral, memory-resident map of active sessions to Blackboard memory regions.

## 5. Alternatives Considered
* **Periodic TTL-based Deletion:** Rejected because sensitive traces could remain vulnerable for the duration of the TTL window.
* **Application-level Deletion:** Rejected as subagents cannot be trusted to self-delete their own traces (the "Malicious Specialist" problem).

## 6. Cross-Cutting Concerns
* **Security (Zero Trust):** Erasure must be hardware-attested. Any failure to erase must trigger an immediate mission-root lockdown.
* **Observability:** Erasure events and scope IDs are logged in the Mesh-Resident Lineage Tracker for auditability.

# Design Doc: Artifact Sovereignty Provider (ASP)
**Status:** Draft
**Created:** 2026-07-08

## 1. Context and Scope
As AI agents move from read-only tasks to active generation (code, build artifacts, media), the risk of "Artifact Hijacking" increases. A compromised subagent or a specialist tool could silently replace a legitimate build output with a backdoored version. Currently, MCP Any secures the *process* of tool calling but lacks a mechanism to verify the *provenance* of the resulting data artifacts.

ASP addresses this by cryptographically binding every file generated by an agent to its parent Mission Root, the generating agent's identity, and the specific hardware enclave (TPM/SEP) where the generation occurred.

## 2. Goals & Non-Goals
* **Goals:**
    * Provide a verifiable cryptographic lineage for all agent-generated files.
    * Ensure artifacts cannot be swapped or modified after generation without breaking the mission-bound signature.
    * Integrate with CI/CD Cache Integrity Guard (CCIG) to secure build pipelines.
* **Non-Goals:**
    * Encrypting the content of the artifacts (ASP focus is on integrity and provenance).
    * Managing long-term storage of artifacts (ASP is a metadata and signing layer).

## 3. Critical User Journey (CUJ)
* **User Persona:** DevSecOps Engineer managing an AI-native CI/CD pipeline.
* **Primary Goal:** Ensure that the Docker image built by an autonomous agent hasn't been compromised by a malicious specialist subagent during the build-cache phase.
* **The Happy Path (Tasks):**
    1. The Primary Agent initiates a "Build" mission with a hardware-attested Mission Root.
    2. The "Docker-Builder" subagent generates an image layer.
    3. ASP intercepts the file-write event, hashes the layer, and signs it with the mission-root key + hardware enclave ID.
    4. The artifact is stored in the build cache along with its ASP-Signature.
    5. During the final assembly, the CI/CD pipeline verifies the signature via the ASP validator before allowing the layer to be included in the final image.

## 4. Design & Architecture
* **System Flow:**
    `[Subagent] -> [ASP Interceptor] -> [Hardware Enclave (Signer)] -> [Storage]`
    `[Storage] -> [ASP Validator] -> [Mission Root Authority] -> [Deployment]`
* **APIs / Interfaces:**
    * `POST /v1/artifacts/sign`: Requests a signature for a newly generated file path.
    * `GET /v1/artifacts/verify`: Validates the signature and lineage of an existing file.
* **Data Storage/State:** ASP maintains a local, hardware-protected "Lineage Manifest" for the duration of the mission.

## 5. Alternatives Considered
* **Standard OS-level integrity (dm-verity):** Rejected because it doesn't provide agent-specific or mission-bound granularity.
* **Simple HMACs:** Rejected as they lack hardware-bound non-repudiation.

## 6. Cross-Cutting Concerns
* **Security (Zero Trust):** ASP keys are rotation-aware and bound to the session-token of the initiating agent.
* **Observability:** All signing and verification events are logged to the Hardware-Locked Audit Trail.

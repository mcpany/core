# Design Doc: Isolated SSH Tool Enclaves
**Status:** Draft
**Created:** 2026-04-07

## 1. Context and Scope
The persistent threat of Remote Code Execution (RCE) in AI agent environments has made host-level tool execution a high-risk liability. Traditionally, MCP servers run as local processes with the same privileges as the agent gateway. A single prompt injection in a tool call can lead to full host compromise.

Isolated SSH Tool Enclaves move execution from the host OS to ephemeral, network-isolated SSH containers. By leveraging patterns seen in OpenClaw v2026.3.22, MCP Any will act as an SSH orchestrator, dispatching tool calls to dedicated enclaves that are destroyed immediately after execution.

## 2. Goals & Non-Goals
* **Goals:**
    * Provide absolute filesystem and network isolation for high-risk tool execution.
    * Enable per-tool resource constraints (CPU, Memory) via container limits.
    * Standardize tool execution across local and remote environments using SSH as a universal transport.
* **Non-Goals:**
    * Replacing simple "Safe" tools (e.g., calculator, weather) that don't require host access.
    * Providing long-lived stateful containers (enclaves are ephemeral by default).

## 3. Critical User Journey (CUJ)
* **User Persona:** Security-Conscious Enterprise Developer
* **Primary Goal:** Execute a potentially unsafe Python script generated by an agent without risking host OS compromise.
* **The Happy Path (Tasks):**
    1. The Agent requests execution of the `run_python` tool.
    2. MCP Any identifies `run_python` as a "High-Risk" tool requiring an enclave.
    3. MCP Any provisions an ephemeral SSH container with a read-only mount of necessary project files.
    4. The tool call is dispatched via SSH to the container.
    5. Results are captured, and the container is immediately terminated and wiped.
    6. The Agent receives the output, knowing it was generated in a safe sandbox.

## 4. Design & Architecture
* **System Flow:**
    ```mermaid
    sequenceDiagram
        Agent->>Gateway: Tool Call (run_python)
        Gateway->>Enclave Manager: Provision Enclave (SSH)
        Enclave Manager->>Docker/K8s: Spin up ephemeral container
        Gateway->>Enclave: Execute command via SSH
        Enclave-->>Gateway: Return STDOUT/STDERR
        Gateway->>Enclave Manager: Destroy Enclave
        Gateway-->>Agent: Tool Result
    ```
* **APIs / Interfaces:**
    * `IsolatedSSHAdapter`: A new adapter type in `server/pkg/adapter` that handles SSH handshakes and command dispatch.
    * `EnclaveProvisioner`: Internal interface for managing container lifecycles.
* **Data Storage/State:**
    * No persistent state in the enclave.
    * Temporary project fragments are mounted as read-only volumes.

## 5. Alternatives Considered
* **gVisor/Wasmtime:** While performant, they require specialized tool packaging. SSH allows for standard MCP servers to run unmodified in a containerized environment.
* **Firecracker MicroVMs:** Offers better isolation but higher startup latency compared to SSH-over-Docker.

## 6. Cross-Cutting Concerns
* **Security (Zero Trust):** Enclaves are network-isolated; even if compromised, they cannot reach the local network or the internet unless explicitly permitted.
* **Observability:** SSH session logs are streamed to the `Config Sandbox Monitor` for real-time audit.

# Design Doc: Attention-Locked Reasoning Anchors (ALRA)
**Status:** Draft
**Created:** 2026-07-01

## 1. Context and Scope
In deep agent swarms, "Context-Window Flooding" (CWF) has emerged as a high-frequency exploit. Malicious or poorly-configured subagents can inject high-entropy "noise" into the shared context, causing mission-critical instructions (the "Mission Root") to be evicted from the LLM's active attention window. This leads to "Reasoning Hijack," where the agent loses its primary objectives and follows the injected noise.

Attention-Locked Reasoning Anchors (ALRA) provides a hardware-bound mechanism to "pin" critical intent fragments at the LLM attention layer. By utilizing specialized KV-cache headers and hardware-attested anchoring, ALRA ensures that core instructions remain immutable and prioritized, regardless of the volume of noise generated by subagents.

## 2. Goals & Non-Goals
* **Goals:**
    * Protect mission-critical instructions from eviction during Context-Window Flooding attacks.
    * Provide a hardware-attested proof that specific "anchors" were present in the attention window during reasoning.
    * Enable dynamic priority-weighting for different context fragments based on mission lineage.
* **Non-Goals:**
    * Increasing the physical context window of the underlying LLM.
    * Automating the entire reasoning process (ALRA is a governance and stability layer).

## 3. Critical User Journey (CUJ)
* **User Persona:** Security-Conscious Swarm Orchestrator
* **Primary Goal:** Ensure that a "System Administrator" agent never forgets its "ReadOnly" constraint, even when a "Log Parser" subagent generates 100k tokens of noise.
* **The Happy Path (Tasks):**
    1. The user initiates a mission with a "Mission Root" intent fragment: `Constraint: Read-Only`.
    2. MCP Any generates an ALRA token for this fragment, cryptographically binding it to the session's TPM.
    3. During execution, a subagent floods the context with thousands of log entries.
    4. The ALRA middleware detects the attention-density spike and applies "Attention-Locking" headers to the `ReadOnly` constraint.
    5. The LLM processes the noisy logs but keeps the `ReadOnly` anchor at the top of its attention priority.
    6. The agent successfully completes the mission while adhering to the constraint.

## 4. Design & Architecture
* **System Flow:**
    ```mermaid
    graph TD
        MR[Mission Root Intent] -->|Sign| AG[ALRA Generator]
        AG -->|Anchor Token| MB[Memory Bus]
        SUB[Subagent Noise] --> MB
        MB -->|Attention Mapping| AGU[Attention Gatekeeper Unit]
        AGU -->|Priority Lock| LLM[LLM Reasoning Engine]
        LLM -->|Hardware Proof| V[Validator]
    ```
* **APIs / Interfaces:**
    * `POST /v1/anchors/lock`: Submits a context fragment for hardware-attested attention locking.
    * `GET /v1/anchors/status`: Returns the current attention-density and anchor-priority scores.
* **Data Storage/State:**
    * Anchors are stored in the Hardware-Attested Memory Shards (HAMS) within the Blackboard.
    * Attention weights are managed in a session-bound cache within the ALRA middleware.

## 5. Alternatives Considered
* **Simple Instruction Repetition:** Rejected because it wastes tokens and can still be overwhelmed by extremely high-entropy noise.
* **Vector DB Retrieval for Constraints:** Rejected due to the "Retrieval Latency" and the risk of retrieval-failure during high-load scenarios.

## 6. Cross-Cutting Concerns
* **Security (Zero Trust):** ALRA tokens are hardware-bound; even if the gateway software is compromised, the anchors cannot be modified without re-attestation.
* **Observability:** The "Attention Heatmap" in the UI allows users to see in real-time which fragments are being prioritized by the LLM.

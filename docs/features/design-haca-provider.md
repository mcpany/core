# Design Doc: Hardware-Attested Cost Attribution (HACA) Provider
**Status:** Draft
**Created:** 2026-07-12

## 1. Context and Scope
As agent swarms become more complex and autonomous, "Economic Squatting" has emerged as a critical stability risk. Specialist subagents or recursive delegations can consume excessive tokens and compute resources without clear visibility into which mission branch is responsible. This leads to budget exhaustion and "Resource Squatting" by rogue or inefficient agents.

The HACA Provider aims to solve this by providing hardware-locked economic transparency. It cryptographically attributes every micro-unit of token spend and every millisecond of GPU time to its specific sub-process lineage, ensuring absolute economic accountability across the mesh.

## 2. Goals & Non-Goals
* **Goals:**
    * Cryptographically bind token and compute usage to a specific hardware-attested mission-root token.
    * Provide a verifiable "Receipt of Attribution" for every tool call or reasoning fragment.
    * Support hierarchical budget reconciliation across deep delegation hops.
    * Enable real-time "Economic Kill-Signals" for mission branches that exceed their HACA-bound limits.
* **Non-Goals:**
    * Managing the actual billing with LLM providers (this is handled by the Billing Proxy).
    * Optimizing the cost of the reasoning process itself.

## 3. Critical User Journey (CUJ)
* **User Persona:** Enterprise AI Ops Manager
* **Primary Goal:** Track and limit the cost of a complex multi-agent codebase migration task.
* **The Happy Path (Tasks):**
    1. The user defines a $50 token budget and a 1-hour time limit for a "Migration Mission."
    2. MCP Any issues a HACA-bound mission-root token.
    3. The Lead Agent delegates tasks to 10 subagents; each subagent receives a child token linked to the HACA lineage.
    4. Every tool call and reasoning fragment generated by subagents is tagged with the HACA lineage and signed by the hardware enclave (TPM).
    5. The HACA Provider monitors the cumulative spend in real-time.
    6. When one subagent branch consumes 80% of the budget unexpectedly, the user is alerted with a detailed "Cost Lineage" map.

## 4. Design & Architecture
* **System Flow:**
    `Agent Request` -> `HACA Middleware` -> `Hardware Enclave (Sign Attribution)` -> `LLM Provider`
    1. **Interception**: HACA Middleware intercepts all outbound reasoning and tool requests.
    2. **Attestation**: The TPM signs the request metadata, including the `Mission-Root-ID` and `Lineage-Path`.
    3. **Usage Tracking**: Upon response, the provider extracts usage metrics (tokens, latency) and updates the lineage-bound budget record.
* **APIs / Interfaces:**
    * `POST /v1/haca/attribute`: Ingests usage metrics and links them to a lineage.
    * `GET /v1/haca/report/{missionId}`: Returns a hierarchical cost breakdown for a mission.
* **Data Storage/State:** Persistent state in the "Economic Registry" (SQLite), with hardware-attested snapshots for non-repudiation.

## 5. Alternatives Considered
* **JSON-based Metadata Headers**: Rejected as they are easily spoofed by subagents. Only hardware-bound signatures provide the necessary rigor for economic security.
* **Centralized Database Tracking**: Rejected as the primary source of truth because it doesn't provide cryptographic proof of lineage to the LLM provider.

## 6. Cross-Cutting Concerns
* **Security (Zero Trust):** All attribution tokens are TPM-signed to prevent spoofing of lineage IDs.
* **Observability:** Real-time cost heatmaps are provided in the "Economic Attribution Viewer" UI.

# Design Doc: Atomic Reasoning Checkpoints (ARC)
**Status:** Draft
**Created:** 2026-07-25

## 1. Context and Scope
In parallel agent meshes (e.g., Claude Code Agent Teams), multiple subagents often mutate the shared Blackboard state simultaneously. When a specific sub-mission fails or diverges, the current "All-or-Nothing" rollback mechanism forces the entire swarm to revert to a previous global state, causing massive progress loss for sibling agents who were succeeding in their respective tasks.

ARC introduces a granular state-management model where agents can create task-specific, local checkpoints on the Blackboard. This allows the orchestrator to perform shard-level rollbacks, isolating failures and preserving the collective reasoning work of the mesh.

## 2. Goals & Non-Goals
*   **Goals:**
    *   Enable agents to create "Named Checkpoints" tied to specific task IDs.
    *   Support shard-level rollbacks that only affect keys modified within a specific task context.
    *   Maintain mission-root consistency across parallel sibling rollbacks.
    *   Provide a "Progress-Safe" commit signal for teammates.
*   **Non-Goals:**
    *   Replacing the global mission rollback for systemic failures.
    *   Managing local subagent filesystem states (ARC focuses on the Shared Blackboard).

## 3. Critical User Journey (CUJ)
*   **User Persona:** Local LLM Swarm Orchestrator managing a coding team.
*   **Primary Goal:** Roll back a failed "Refactoring Specialist" without losing the documentation generated by the "Docs Specialist."
*   **The Happy Path (Tasks):**
    1.  The Doc Specialist creates an ARC checkpoint `docs_v1` before writing to the Blackboard.
    2.  The Refactoring Specialist creates an ARC checkpoint `refactor_v1` before editing source metadata on the Blackboard.
    3.  The Refactoring Specialist fails its unit test and signals a "Reasoning Divergence."
    4.  The Orchestrator triggers an `ARC_ROLLBACK(refactor_v1)`.
    5.  MCP Any reverts only the keys modified by the Refactoring Specialist.
    6.  The Doc Specialist's work remains committed and visible.

## 4. Design & Architecture
*   **System Flow:**
    ```mermaid
    graph TD
        Agent[Subagent] -->|Create Checkpoint| ARC[ARC Service]
        ARC -->|Tag Keys| BB[Blackboard Store]
        Agent -->|Fail| ORCH[Orchestrator]
        ORCH -->|Rollback Shard| ARC
        ARC -->|Revert Tagged Keys| BB
    ```
*   **APIs / Interfaces:**
    *   `POST /checkpoint/create`: Parameters: `task_id`, `checkpoint_name`.
    *   `POST /checkpoint/rollback`: Parameters: `checkpoint_name`.
    *   `POST /checkpoint/commit`: Finalizes the shard and removes the temporary rollback logs.
*   **Data Storage/State:**
    *   Utilizes SQLite `SAVEPOINT` and `ROLLBACK TO` logic mapped to specific key-ranges or task tags.
    *   Metadata table in the Blackboard tracking key ownership per task.

## 5. Alternatives Considered
*   **Full Blackboard Snapshots:** Rejected due to high storage overhead and sibling progress loss.
*   **Client-Side State Management:** Rejected because it doesn't prevent "Context Smearing" where other agents read un-verified state.

## 6. Cross-Cutting Concerns
*   **Security (Zero Trust):** Checkpoints are bound to hardware-attested task tokens. One subagent cannot roll back another subagent's shard without authorization.
*   **Observability:** Integrated with the `Swarm Rollback Dashboard` for real-time visualization of shard-level recovery.

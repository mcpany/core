# Design Doc: Context-Aware Shard Isolation (CASI) Middleware
**Status:** Draft
**Created:** 2026-06-07

## 1. Context and Scope
In horizontal teammate swarms (e.g., Claude Code Agent Teams), agents often share a common teammate mailbox for coordination. However, research indicates that "Shard Pollution"--where an agent "sees" state fragments from a parallel branch of the mission--is the leading cause of "Reasoning Drift" and hallucination.

MCP Any needs to implement CASI to semantically isolate mailbox shards. This ensures that teammates can only access state fragments relevant to their active task context, maintaining the cognitive integrity of parallel reasoning paths.

## 2. Goals & Non-Goals
* **Goals:**
    * Perform real-time semantic analysis of mailbox messages to identify task-bound shards.
    * Enforce shard isolation, preventing cross-teammate state pollution.
    * Provide a forensic interface for inspecting fragment-level access violations.
* **Non-Goals:**
    * Encrypting mailbox contents (handled by the T2T Encryption Bridge).
    * Managing global task list synchronization (handled by the Lock-Free Mesh Arbiter).

## 3. Critical User Journey (CUJ)
* **User Persona:** Multi-Agent System Developer
* **Primary Goal:** Ensure that Teammate A (UI Specialist) cannot see the state fragments generated by Teammate B (Backend Specialist) unless a specific shard-merge is authorized.
* **The Happy Path (Tasks):**
    1. Teammate A and Teammate B join a mission.
    2. MCP Any assigns them to separate, isolated mailbox shards based on their assigned roles.
    3. Teammate A writes UI state to their shard.
    4. Teammate B attempts to read the UI state but is blocked by the CASI middleware.
    5. Lead Agent authorizes a shard-merge, allowing Teammate B to ingest the UI state.

## 4. Design & Architecture
* **System Flow:**
    ```mermaid
    graph TD
        A[Teammate A] -->|Post Message| CASI[CASI Middleware]
        CASI -->|Semantic Check| ShardA[Shard A: UI Context]
        B[Teammate B] -->|Read Request| CASI
        CASI -->|Isolation Check| Denied[Access Denied: Shard Mismatch]
        Lead[Lead Agent] -->|Authorize Merge| CASI
        CASI -->|Allow| ShardA
        ShardA --> B
    ```
* **APIs / Interfaces:**
    * `shard:mount`: Creates a semantically isolated mailbox shard.
    * `shard:read`: Restricted read access based on active task context.
    * `shard:merge`: Authoritative merge of two isolated shards.
* **Data Storage/State:** Shards are managed as addressable memory regions within the Shared KV Store.

## 5. Alternatives Considered
* **Role-Based Access Control (RBAC):** Rejected because roles are too static for dynamic agent meshes; isolation must be based on the real-time reasoning context.
* **Full Process Isolation:** Rejected due to the high overhead and latency of cross-process state transfer.

## 6. Cross-Cutting Concerns
* **Security (Zero Trust):** CASI utilizes RMA tokens to verify the mission-root authority of shard-merge requests.
* **Observability:** Shard isolation violations are surfaced in the CASI Shard Inspector UI.

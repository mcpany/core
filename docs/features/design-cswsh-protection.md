# Design Doc: Cross-Site WebSocket Hijacking (CSWSH) Protection
**Status:** Draft
**Created:** 2026-03-10

## 1. Context and Scope
The February 2026 OpenClaw RCE (CVE-2026-25253) highlighted a critical vulnerability in agentic developer tools: malicious websites can connect to local WebSocket servers if they do not validate the `Origin` header. Since MCP Any often acts as a gateway or adapter for sensitive local tools, it must implement robust protections to ensure that only authorized clients (e.g., the local UI or specific agent CLI) can initiate WebSocket handshakes.

## 2. Goals & Non-Goals
* **Goals:**
    * Implement mandatory `Origin` header validation for all WebSocket listeners.
    * Introduce a handshake-token mechanism (CSRF-style) for WebSocket upgrades.
    * Provide a configurable "Origin Allowlist" that defaults to strict `localhost`.
    * Enforce same-site cookie attributes for any session-based WebSocket authentication.
* **Non-Goals:**
    * Implementing full-blown OAuth for local WebSocket connections (focus is on transport security).
    * Protecting against physical host access or root-level compromise.

## 3. Critical User Journey (CUJ)
* **User Persona:** Developer using the MCP Any UI to monitor local agents.
* **Primary Goal:** Prevent a malicious website in the background from hijacking the MCP Any control plane.
* **The Happy Path (Tasks):**
    1. The MCP Any UI initiates a WebSocket connection to `ws://localhost:3000/v1/ws`.
    2. The browser automatically includes the `Origin: http://localhost:3000` header.
    3. MCP Any validates the `Origin` against its allowlist.
    4. MCP Any also checks for a `sec-mcp-token` provided in the handshake query or header (generated by the UI on load).
    5. The connection is upgraded and established.

## 4. Design & Architecture
* **System Flow:**
    `Client (Browser/Agent)` -> `WebSocket Upgrade Request` -> `CSWSH Middleware` -> `WebSocket Handler`
    1. **Origin Check**: The middleware extracts the `Origin` header. If it doesn't match the configured allowlist, the request is rejected with `403 Forbidden`.
    2. **Token Validation**: For sensitive endpoints, a one-time or session-bound handshake token is required.
    3. **Handshake Logic**: Standard `gorilla/websocket` or equivalent upgrader configuration.
* **APIs / Interfaces:**
    * New configuration field: `security.websocket.allowed_origins: ["http://localhost:3000"]`
    * New configuration field: `security.websocket.require_token: true`
* **Data Storage/State:**
    * Transient handshake tokens stored in memory (e.g., LRU cache) or verified via HMAC.

## 5. Alternatives Considered
* **Relying solely on `localhost` binding**: Rejected, as shown by CVE-2026-25253, this does not prevent cross-site hijacking.
* **Requiring SSH tunneling**: Too high friction for local development workflows.

## 6. Cross-Cutting Concerns
* **Security (Zero Trust)**: Follows the principle of "Implicit Distrust" for all browser-initiated connections.
* **Observability**: Log all rejected WebSocket handshakes with the source `Origin` and `User-Agent` to help identify attack attempts.

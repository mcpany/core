# Design Doc: Reasoning-Path Watermarker (RPW)
**Status:** Draft
**Created:** 2026-07-09

## 1. Context and Scope
In heterogeneous agent meshes, agents increasingly share and ingest each other's "Internal Monologues" to maintain shared context and mission alignment. However, the rise of "Monologue Forgery" has introduced a critical vulnerability: malicious agents can spoof or tamper with reasoning traces, leading to intent hijacking and cross-framework coercion.

The Reasoning-Path Watermarker (RPW) provides a cryptographic solution by embedding hardware-attested watermarks directly into the reasoning token stream. This ensures that every reasoning fragment is non-repudiable and can be verified by any teammate in the mesh.

## 2. Goals & Non-Goals
* **Goals:**
    * Implement a system for embedding TPM-signed cryptographic watermarks into agent reasoning tokens.
    * Provide a low-latency "RPW Validator" for real-time verification of ingested reasoning traces.
    * Support "Multi-Hop Reasoning Provenance" where watermarks are chained across delegations.
    * Neutralize "Monologue Forgery" attacks in heterogeneous meshes.
* **Non-Goals:**
    * Encrypting the reasoning content (handled by SRM/HAPE).
    * Modifying the core LLM generation process (watermarks are applied at the transport/proxy layer).

## 3. Critical User Journey (CUJ)
* **User Persona:** Heterogeneous Swarm Auditor
* **Primary Goal:** Verify that a "Security Specialist" agent's reasoning trace was actually generated by the verified specialist and not spoofed by a lower-trust subagent.
* **The Happy Path (Tasks):**
    1. Specialist Agent generates a reasoning fragment.
    2. RPW Middleware intercepts the fragment and requests a TPM signature bound to the agent's hardware identity.
    3. RPW Middleware embeds the signature as a "Watermark" token in the fragment's metadata/stream.
    4. Recipient Agent receives the fragment via the T2T Bridge.
    5. Recipient Agent's RPW Validator verifies the watermark against the Sender's public key (stored in the FSI Provider).
    6. If verified, the reasoning is ingested; otherwise, a "Forgery Alert" is triggered.

## 4. Design & Architecture
* **System Flow:**
    `[Reasoning Fragment] -> [RPW Signer (TPM)] -> [Watermarked Fragment] -> [T2T Transport] -> [RPW Validator] -> [Reasoning Ingestion]`
* **APIs / Interfaces:**
    * `rpw.SignFragment(fragment []byte, identity HardwareIdentity) -> []byte`: Appends a watermark to a fragment.
    * `rpw.VerifyFragment(watermarkedFragment []byte) -> (senderID string, ok bool)`: Extracts and verifies the sender identity.
* **Data Storage/State:**
    * **Watermark Registry:** A session-bound cache of recently verified watermarks to optimize repeat fragment validation.

## 5. Alternatives Considered
* **Out-of-Band Signatures:** Rejected as they increase "Coordination Tax" and are easier to strip or mismatch during streaming. In-stream watermarking is more resilient.
* **Full SRM Encryption:** Complements RPW but doesn't solve the provenance problem for shared "unsealed" fragments.

## 6. Cross-Cutting Concerns
* **Security (Zero Trust):** RPW signatures must be hardware-bound (TPM/SEP) to prevent subagents from stealing and reusing watermarking keys.
* **Observability:** Verification failures and provenance chains are visualized in the "Reasoning Integrity Dashboard."

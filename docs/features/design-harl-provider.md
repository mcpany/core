# Design Doc: Hardware-Attested Reasoning Lineage (HARL) Provider
**Status:** Draft
**Created:** 2026-07-25

## 1. Context and Scope
As agents become more autonomous and are deployed in high-trust environments (e.g., CI/CD pipelines, financial systems), the requirement for non-repudiation moves from the tool-call layer to the reasoning path itself. Current models allow for "Intent Shadowing" where a subagent can generate a legitimate-looking tool call driven by a compromised internal reasoning state.

The Hardware-Attested Reasoning Lineage (HARL) Provider addresses this by creating a cryptographically signed, hardware-bound record of the agent's *entire* cognitive path. This includes internal monologues, rejected reasoning branches, and intermediate state transitions, ensuring that every action is linked to an untamperable audit trail.

## 2. Goals & Non-Goals
* **Goals:**
    * Provide TPM-signed hashes of the full reasoning trace for every agent session.
    * Enable non-repudiable auditing of autonomous agent decisions.
    * Integrate with the RIV v2 provider to ensure lineage integrity across distributed nodes.
    * Support "Proof of Reasoning" verification for external auditors without exposing raw context (via PPA Hub).
* **Non-Goals:**
    * Modifying the model's weights or internal inference logic.
    * Providing real-time reasoning (HARL is an attestation and logging layer).

## 3. Critical User Journey (CUJ)
* **User Persona:** Security Compliance Auditor
* **Primary Goal:** Verify that a high-value code commit generated by an AI agent was driven by the authorized mission-root and not an injected subagent instruction.
* **The Happy Path (Tasks):**
    1. The Auditor accesses the "HARL Trace Inspector" in the UI.
    2. They select the session ID associated with the commit.
    3. HARL retrieves the TPM-signed trace hash from the hardware root.
    4. The inspector verifies the hash against the stored reasoning monologue.
    5. The Auditor confirms that the complete "Chain of Reason" aligns with the hardware-attested mission manifest.

## 4. Design & Architecture
* **System Flow:**
    ```mermaid
    graph TD
        A[Agent Monologue] --> B[HARL Provider]
        C[Internal State] --> B
        B --> D[TPM 2.0 Enclave]
        D --> E[Full-Trace Hash]
        E --> F[HARL Token]
        F --> G[Non-Repudiable Audit Log]
    ```
* **APIs / Interfaces:**
    * `POST /v1/harl/attest`: Submits a reasoning fragment for hardware-bound hashing.
    * `GET /v1/harl/verify`: Validates a HARL token against a provided trace.
* **Data Storage/State:**
    * Trace hashes are stored in the secure segment of the Blackboard, indexed by hardware enclave ID.

## 5. Alternatives Considered
* **Software-based Logging:** Rejected due to the risk of log tampering by compromised agents.
* **Periodic Snapshots:** Rejected as it lacks the granularity required for full-trace non-repudiation.

## 6. Cross-Cutting Concerns
* **Security (Zero Trust):** HARL tokens are hardware-locked; they cannot be migrated or replayed across disparate hardware roots.
* **Observability:** Integrated with the "HARL Trace Inspector" for forensic analysis.
